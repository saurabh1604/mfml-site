## W10 · `#w-fog` — walking in the fog (3D stage `#fg-3d`, `.stage3d.tall`)
The intuition anchor for the whole unit: you cannot see the landscape, only the ground under your feet.
Landscape: `f(x,y) = 1.1·exp(−((x−1.2)²+(y−0.8)²)/1.6) − 1.6·exp(−((x+1.1)²+(y+0.6)²)/2.2) − 0.9·exp(−((x−0.4)²+(y+1.9)²)/1.4) + 0.06·(x²+y²)` on `[−3.2,3.2]²` (a hill, a deep valley, a shallow valley) — write the analytic gradient by hand and check it numerically once. ZS ≈ .9.
Stage: the FULL landscape is present as a lit `prim.surface` (res 80, ramp) but rendered **dim and desaturated** through fog: use `fadeAttr` to set per-vertex `vis` = a smooth function of distance from the hiker: 1 inside radius R·0.55, → 0.06 beyond R (rewrite `vis` every frame the hiker moves; keep a floor grid faint everywhere). Inside the disc the surface is fully lit — the student sees a glowing circle of ground moving through darkness. At the hiker: a glowing `prim.dot` (s4) + halo (`sparkTex`), the **tilt arrow** (s2, uphill, `prim.arrow`, length ∝ |∇f| capped at 1.1) and the **step arrow** (s3). A thin `tube` down to the floor. Trail: a `ribbon` (s3) of visited points; behind the fog radius the trail stays visible (it's memory, not sight). Optional: when `fg-lift` ▶ "lift the fog" is pressed, tween all `vis` → 1 over 1.4 s so the whole landscape is revealed with the trail on it, then hold; `fg-fog` "fog back" tweens it back.
Controls: sliders `fg-r` (fog radius R ∈ [0.35,2.5], default 0.9), `fg-g` (step γ ∈ [0.05,0.6], default 0.25); presets `[data-p]` for the start: `ridge` (0.2, 1.9), `slope` (2.4, −1.4), `saddleish` (−0.2, −0.2) → set the hiker there, clear the trail. Buttons: `fg-step` "one step" (tween the hiker 0.35 s along −γ∇f), `fg-play` ▶ "walk" (up to 40 steps, 0.32 s each, stop when |∇f| < 0.02 → pulse the dot, HUD `reached a flat spot`), `fg-lift`, `fg-fog`, `fg-reset`.
Also allow the student to **drag the hiker** with `grab(handle, onDown, onMove)` + `picker` against the surface mesh (as Unit 6 did): onDown returns true when the pointer is within ~0.35 units of the hiker's screen position (raycast the surface, compare the hit to the hiker), onMove sets the hiker to the hit point (clamped to the domain) and redraws (clears the trail).
HUD: `height f = … · tilt |∇f| = … · steps …`. Readout: `position (x, y) = (…, …)`, `the ground tilts uphill toward (…, …)` (the unit gradient direction), `next step = −γ∇f = (…, …)`, `steps taken = … · height fallen = …`. Verdict: info `you can only feel the tilt under your feet — and that is enough` at start; good `✓ flat ground — the walk is over (a valley bottom)` when converged in a valley (f″ test: use the Hessian's determinant/sign numerically via finite differences: det > 0 and fxx > 0); bad `✗ flat ground on a HILLTOP — a nudge would send you rolling` if fxx < 0 (only reachable by dragging exactly to the hilltop; fine if it never triggers); after `lift`: info `two valleys — the walk found the one downhill from where it started`.

## W11 · `#w-race` — three ways to walk: batch vs minibatch vs stochastic (3D stage `#rc-3d` `.stage3d.tall` + side SVG `#rc-curves` 320×220 + a scoreboard)
The centrepiece. The same data as W9 (`N = 40`, the LCG points, loss `L(a,b) = (1/N)Σ(yᵢ − a xᵢ − b)²`, minimiser computed in code) as a lit 3D bowl over `a∈[−1.5,4.5], b∈[−2,3]` with lifted contours. **Three walkers** start at the same point `(3.6, −1.6)`:
- **batch** (s1, "looks at all 40 points every step"), gradient = full gradient;
- **minibatch** (s7, "looks at |S| points", slider `rc-batch` mapped to {2,4,8,16}, default 8), gradient over a fresh LCG-drawn subset each step (separate deterministic stream so runs are reproducible);
- **stochastic** (s4, "looks at 1 point"), one random point per step.
Each has a glowing dot + halo on the surface, its own coloured `ribbon` trail, and a small sprite label (`batch`, `mini 8`, `sgd`). Learning rate slider `rc-g` (γ ∈ [0.02,0.35], default 0.12) shared; tab `rc-mode`: **`steps`** (default; every walker takes one step per tick — the fair-per-step view) | **`budget`** (per tick the three advance by equal *data touched*: batch moves 1 step per 40 units, mini one per |S|, sgd one per 1 — the fair-per-cost view: SGD sprints while batch is still reading). Tab `rc-lr`: `constant` | `decay` (γₜ = γ/(1+0.05t), applied to all three).
▶ `rc-play` runs 1200 units of data budget (≈ 30 batch steps / 150 mini-8 steps / 1200 sgd steps) choreographed at ≈ 40 data-units per 0.1 s (cap the sgd trail to the last 400 points for performance; rebuild ribbons every few ticks, not every frame); `rc-step` advances one tick; `rc-reset`.
Side SVG `#rc-curves`: **loss vs data touched** (x: 0…1200 data units, y: log10 L mapped), three curves in the walker colours, dashed line at L*. A legend. This chart IS the lesson: per unit of data, sgd/minibatch fall far faster; batch is smooth but slow; with constant γ, sgd never settles (jitter floor), with decay it does.
Scoreboard (`#rc-board`, three `.cell`-like chips or a `.plain` table): per walker `steps taken · data touched · L now · distance to (a*,b*)`; highlight the leader (lowest L) with a glow class.
HUD on the stage: `data touched: … · batch L = … · mini L = … · sgd L = …`.
Readout: `every step: batch reads 40 points · minibatch reads |S| = … · stochastic reads 1`, `after … data units: batch took … steps, minibatch …, stochastic …`, `noise of the gradient estimate ∝ 1/√|S|: batch 0 · mini … · sgd 1 (relative)`, `best: a* = …, b* = …, L* = …`.
Verdict: in `steps` mode info `per step, batch is the smoothest — but each of its steps costs 40× a stochastic one`; in `budget` mode good `✓ per point of data read, the noisy walkers get to the bottom first — that is why deep learning trains on minibatches`; with `decay` add `— and with a decaying γ the jitter dies, so stochastic finally settles` (append to the verdict text).
Presets `[data-p]`: `fair-steps` (mode steps, constant), `fair-cost` (mode budget, constant), `cost-decay` (mode budget, decay), `big-batch` (|S| = 16, budget).
